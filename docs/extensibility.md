# 扩展性与存储边界

更新日期：2026-10-18。本文记录设置 KV、独立凭据表及多存储引擎的评估。**仓储接口隔离是明确要求；受控 KV 和保留独立凭据表作为本阶段工程基线，尚无正式运行代码或数据库迁移。** 一期仍只实现 MySQL，暂不接入其他数据库、外部登录或插件系统。

## 1. 系统设置：采用受控 KV

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| 当前四字段的单行表 | 数据库直接约束类型和范围；一行版本与锁最简单 | 每增加配置项通常要改列，模块之间容易共同修改一张表 |
| 无约束 key/value 字符串 | 表结构改动少 | 类型、默认值、敏感信息和键名容易失控，校验分散，难以安全演进 |
| 注册表约束的 KV | 新增内置配置通常不必改表；可以按命名空间归属模块 | 需要集中定义与校验、缺失键处理，以及多行一致性设计 |

对后续会逐步增加模块的 OctoDCP，采用第三种。它保留存储形态的扩展性，同时对调用方保持有类型的配置接口，不让业务代码到处调用 `Get("随便一个键")`。

每个设置定义至少包含：name、类型、默认值、校验函数、所属模块、是否允许控制台修改、对应的公开字段。`system_setting.name` 是主键，保存配置名，`value` 保存 JSON 类型值。定义注册表是代码，不是在数据库再建一套可编程配置语言。当前所有设置均非敏感；秘密材料走部署配置或未来专门的凭据存储，不能借“sensitive=true”就把明文放进 KV。

当前映射：

| 存储 name | 对外字段 | 类型与限制 |
| --- | --- | --- |
| `site.name` | site_name | string，1–40 个码点 |
| `site.timezone` | timezone | string，合法 IANA 时区 |
| `auth.registration_enabled` | registration_enabled | boolean |
| `auth.session_ttl_days` | session_ttl_days | integer，1–30，默认 30；新会话的滑动续期窗口 |

值使用 JSON 保留类型，不能把布尔值保存成 `"false"` 字符串。当前各键不允许 null，单值上限建议 16 KiB。键由服务端定义，最长 96 个 ASCII 字符，采用小写命名空间；前端仍只修改四个明确字段，不提供“新增任意配置”或全库 KV 导入接口。

安装种子事务创建全部必需键。新增键需要一起交付定义、默认值补齐迁移及相关接口/页面；键重命名或含义变化必须做数据迁移，不能把已有值当作缺省值悄悄替换。启动校验必需键，缺失、类型不符或范围错误进入维护状态。保留未识别命名空间的数据而不自动清除，业务只使用当前注册表声明的键。

### 多键并发与版本

多行 KV 不能再借用单行 `row_version`。本稿使用每键版本 + 设置视图聚合 ETag，不增加第八张版本计数表，也不把可变计数塞进不可由业务修改的安装记录。

1. 设置视图读取自己涉及的完整键集，四个值及行版本必须来自同一读取快照。
2. 应用按 name 排序，对“定义版本、name、行版本、有效类型值”做固定编码并取 SHA-256。行版本以字符串编码，JSON 数值按注册类型校验后编码，不依赖数据库返回 JSON 的空白、字段顺序或数值扫描形式。
3. 设置 API 返回该摘要作为 version 和强 ETag。它只是并发版本，不承担认证功能；客户端原样回传，不解析或递增。
4. 修改时先重新验证操作者，再在事务内按 name 顺序锁定该视图完整配置集、重新计算并比较版本；随后只更新发生变化的配置及其行版本，与一条白名单审计事件一起提交。
5. 行版本避免值被改回原值后的旧请求通过检查。无变化不递增版本；未来不同设置分组可有自己的键集和 ETag，减少无关模块的编辑冲突。

注册流程锁定并重新读取 `auth.registration_enabled`，与管理员关闭注册在同一记录上排序。不能用陈旧的进程缓存决定是否允许注册。事务仓储需要提供“读取这组设置用于原子修改”的语义，其他存储适配器可以用锁或等价并发控制实现，但必须通过相同竞争场景验证。

## 2. 用户密码：保留独立表

若一期永远只有一个本地密码，把哈希、改密标记和修改时间放进 `user` 确实少一次关联，也少一张表；这是可行的最简结构。独立表本身不等于更强的数据库权限隔离，同一个数据库账号仍可能查询它。

已确认表名为 `user_password`，领域模型为 UserPassword。名称直接说明该表只保存本地密码相关数据；外部身份、MFA、通行密钥以后分别建模，不将本表扩成多种凭据的混合容器。

本项目已经计划接入外部系统，用户的认证方式也可能扩展。保留独立密码表，原因是：

- 用户代表协作身份与资料；本地密码只是一个登录方式，生命周期不同。
- 常规用户列表、头像和审计操作者查询不必加载密码字段，降低映射或序列化误用的机会。真正的保护仍依赖 DTO 白名单与服务授权。
- 一期正常/禁用的本地账号恰好有一行凭据；删除账号移除凭据。将来只有外部登录的用户可以没有这一行，不需要伪造随机密码占位。
- `user.auth_version` 继续统一控制全部登录会话，不放进本地凭据表；角色变更或禁用仍能影响未来不同来源的会话。
- 以后可另建外部身份关联，例如 provider_id + subject 唯一映射到 user_id；不能按显示名或邮箱自动合并身份。外部令牌、MFA 认证器等也各有模型，不扩成一张万能凭据表。

当前仍是一对零或一的轻量表：user_id 主键、password_hash、require_password_change、password_changed_at。不预建 provider、MFA、密码历史等字段，也不为 bcrypt 再增加盐表。未来“一个用户是否必须有可用登录方式”的策略在身份模块内演进，不让用户资料模块决定。

## 3. 仓储与事务接口

数据访问组件必须保留可替换接口，sqlx 只存在于 MySQL 适配器。边界是用例需要的操作、查询与原子性，不是给 sqlx 的每个方法套一层同名接口。

建议结构：

```text
internal/modules/identity/
  model.go                   # 领域类型与 ID
  repository.go              # UserRepository 等最小用例端口
  unit_of_work.go            # 本模块需要的事务仓储集合接口
  service.go                 # 只依赖上述接口及领域规则
internal/modules/settings/
  definitions.go             # 设置定义与类型校验
  repository.go              # 设置视图与条件写入端口
  service.go
internal/store/
  mysql/                     # sqlx 连接、行结构、SQL、端口实现与事务装配
  migrations/mysql/          # MySQL 方言迁移；未来按引擎增加目录
```

以下是接口形态示意，类型由用例所属模块定义；并非新增生产代码：

```go
type AccountUnitOfWork interface {
    Within(ctx context.Context, fn func(AccountStores) error) error
}

type AccountStores interface {
    Users() UserRepository
    Passwords() UserPasswordRepository
    Sessions() SessionRepository
    AvatarBindings() AvatarBindingRepository
    Audit() AuditAppender
}
```

所有返回的仓储绑定同一次事务，只在回调内有效。SQL 适配器在内部创建一个 sqlx.Tx，成功提交、失败回滚；回调中误用外部连接池会破坏事务，必须通过装配与测试避免。服务接口不出现 `*sqlx.DB`、`*sqlx.Tx`、`*sql.Tx`、SQL 字符串或驱动行结构。

接口返回领域对象或明确的查询投影；筛选使用 typed query、白名单排序、分页/游标，条件更新携带期望版本。驱动的唯一冲突、超时等错误翻译成稳定业务错误，不能把 MySQL 错误码暴露成领域契约。

多模块写入由实际用例定义小范围协作端口，适配器装配实现，不让模块服务互相调用并各开一个事务，也不建立依赖所有模块的全局巨型 Repository。接口定义文件只依赖必要领域类型，不能反向导入 MySQL 适配器；跨模块导入方向在实现时保持无循环。

### 其他引擎需要证明什么

更换驱动不等于获得其他数据库兼容性。sqlx 的扫描辅助不处理所有 SQL 方言、JSON、索引、ID 生成及事务语义差异。未来的适配器需要实现仓储、UnitOfWork 与独立迁移，并复用一套契约检查：

- 用户名唯一、逻辑删除、稳定已发放用户 ID；ID 对外仍使用字符串，不因换库改变现有资源链接。
- 创始人保护、管理员同时互相禁用/降级时的授权重新检查。
- 用户/凭据/会话/审计的原子写入、版本冲突和会话立即失效；滑动续期不能恢复已撤销/到期会话，清理不能误删已续期会话。
- 设置多键快照与条件更新、关闭注册与进行中注册的竞争。
- 头像唯一绑定、权限、草稿到期及垃圾清理的竞争。

支持行锁的引擎可以实现锁定语义；其他引擎若采用事务加条件写入，必须保证同等业务结果。不能为方便更换引擎而接受账号已变更但审计未落盘、禁用后旧会话继续授权等差异。没有足够多对象原子能力的存储，需要重新设计并评估，不能声称任意引擎都能直接接入。

一期只交付 MySQL 适配器；接口和契约先稳定，不提前写 PostgreSQL/SQLite 实现，也不增加运行时插件加载器。

## 4. 其他保留与暂缓的扩展点

| 边界 | 一期保留什么 | 暂缓什么 |
| --- | --- | --- |
| 头像文件 | 文件存储接口、服务端生成的 key；API URL 与磁盘路径分离 | 对象存储实现、跨用户去重、任意附件平台 |
| 密码 | 小范围 Hash / Verify / NeedsRehash 封装，自描述哈希字符串 | 万能密码插件、默认叠加 pepper、MFA 实现 |
| 主密钥与密文 | 格式版本、字段用途 AAD、独立用途派生 | 自动密钥轮换、外部 KMS 接入 |
| 账号与授权 | 稳定 user_id、独立身份模块、明确系统策略 | 把项目角色混入 admin/user，通用动态 RBAC 引擎 |
| 时间 | 过期判断使用可注入时钟，事务内外使用明确时间点 | 自建全站调度框架 |
| API | DTO 与数据库结构分离，稳定业务错误与不透明版本 | 让表列或 KV 注册表自动生成所有公开写接口 |
| 审计 | 白名单事件、与业务同事务、稳定动作命名 | 把审计当消息队列；需要可靠通知时再加 outbox |
| 前端 | 按功能模块装配路由、页面与 API 服务，统一主题语义变量 | 运行时加载前端插件、预建空项目/工作流页面 |

后续项目、团队、仓库、集成连接、工作流定义及执行记录都有身份、关联、权限和生命周期，应各建领域模型与表。KV 只用于低频配置，不承担业务实体和任意秘密存储。扩展点以已经出现的边界为依据，不为尚未清楚的 AI 决策或 Graph 执行提前规定协议。
